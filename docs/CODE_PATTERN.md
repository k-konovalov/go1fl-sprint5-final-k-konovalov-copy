## 1. Организация кода в пакеты

### 1.1 Одна директория — один пакет

Из [`Пакеты и импорт (1).md`](../Пакеты%20и%20импорт%20(1).md): все файлы директории принадлежат одному пакету,
имя пакета совпадает с именем директории. Исключение — `_test.go`, которые могут объявлять другой пакет.

Применение: каждая из пяти директорий в [`internal/`](internal) содержит ровно один файл реализации с
`package <имя_директории>`.

### 1.2 Мелкие пакеты по назначению

Рекомендация — дробить код на небольшие пакеты с информативными именами, избегая `util`, `base`, `tools`, `lib`, `common`.

Применение и обоснование имён:

| Пакет | Ответственность |
|---|---|
| [`spentenergy`](internal/spentenergy/spentenergy.go:1) | расчёты: дистанция, скорость, калории |
| [`personaldata`](internal/personaldata/personaldata.go:1) | персональные данные и их вывод |
| [`trainings`](internal/trainings/trainings.go:1) | разбор и описание тренировок |
| [`daysteps`](internal/daysteps/daysteps.go:1) | разбор и описание прогулок |
| [`actioninfo`](internal/actioninfo/actioninfo.go:1) | агрегация через интерфейс |

### 1.3 Минимальный экспорт

«Экспортируемые элементы представляют собой внешний интерфейс вашего пакета. Пусть он будет минималистичным.»

Применение:

- экспортируем ровно то, что требует ТЗ: `Distance`, `MeanSpeed`, `RunningSpentCalories`, `WalkingSpentCalories`,
  `Personal`, `Training`, `DaySteps`, `DataParser`, `Info`;
- константы (`mInKm`, `minInH`, `stepLengthCoefficient`, `walkingCaloriesCoefficient`) остаются неэкспортируемыми;
- экспорт переменных не практикуем — только функции и типы.

### 1.4 Константы вместо магических чисел

В [`spentenergy`](internal/spentenergy/spentenergy.go:8) константы уже объявлены блоком `const (...)`. Используем их,
не дублируя литералы в коде расчётов.

### 1.5 Standard Go Project Layout

Из заметки: `cmd/` для бинарников, `internal/` для основного кода, запрещённого к импорту извне модуля.

Применение: [`cmd/tracker/main.go`](cmd/tracker/main.go:1) — единственная точка входа, не редактируется;
весь код — в `internal/`, что гарантирует недоступность пакетов за пределами модуля.

### 1.6 Отсутствие циклов импорта, связь через интерфейс

Из заметки: циклический импорт — ошибка компиляции.

Применение: направленный граф зависимостей
`main → {actioninfo, daysteps, trainings, personaldata}`, `{daysteps, trainings} → {personaldata, spentenergy}`.
[`actioninfo`](internal/actioninfo/actioninfo.go:1) объявляет интерфейс у себя (потребитель определяет интерфейс),
поэтому не импортирует `trainings`/`daysteps` и цикл невозможен.

## 2. Модули и зависимости

### 2.1 Модуль как единица версионирования

Из [`Модули — Яндекс Практикум.md`](../Модули%20—%20Яндекс%20Практикум.md): модуль — коллекция пакетов с общим
версионированием; имя модуля в [`go.mod`](go.mod:1) используется как префикс импорта.

Применение: `module github.com/Yandex-Practicum/tracker`, все внутренние импорты строятся от этого префикса.
Модули не вкладываем друг в друга.

### 2.2 `go.mod` как единственный источник зависимостей

Из [`Внешние зависимости — Яндекс Практикум.md`](../Внешние%20зависимости%20—%20Яндекс%20Практикум.md): зависимости
описываются в `go.mod`, а `go.sum` фиксирует контрольные суммы для воспроизводимости.

Применение: `testify` — единственная внешняя зависимость, она нужна только тестам. Реализация не должна добавлять
новых зависимостей: все задачи решаются стандартной библиотекой (`fmt`, `log`, `strings`, `strconv`, `time`, `errors`).

### 2.3 `go mod tidy` как гигиена

`go mod tidy` приводит `go.mod`/`go.sum` в соответствие с фактическими импортами; это первый шаг [`PLAN.md`](PLAN.md).

## 3. Эмбеддинг и композиция

### 3.1 Композиция вместо наследования

Из [`Эмбеддинг — Яндекс Практикум.md`](../Эмбеддинг%20—%20Яндекс%20Практикум.md): Go не поддерживает наследование;
структура «включает» другую структуру, а не «является» ею.

Применение: `Training` и `DaySteps` включают `personaldata.Personal` — их нельзя привести к `Personal`,
но они получают его поля (`Name`, `Weight`, `Height`) и метод `Print()`.

### 3.2 Переиспользование полей и методов через встраивание

Встроенный тип передаёт внешней структуре свои поля и методы «как если бы она сама их содержала».

Применение: `personaldata.Personal` встроен без имени поля, поэтому:

- поля доступны напрямую: `t.Weight`, `ds.Height` (используется в тестах и в `main.go`);
- метод `Print()` доступен как `t.Print()` и `ds.Print()`, что требует [`main.go`](cmd/tracker/main.go:36);
- доступ по полному пути `t.Personal.Print()` остаётся возможным — применяем его, только если понадобится явность.

### 3.3 Затенение методов и выбор получателя

Правила из заметки: метод внешней структуры затеняет метод встроенного типа; дубликаты имён на одном уровне
вложенности дают ошибку только при использовании.

Применение:

- `Training` и `DaySteps` **не** объявляют собственный `Print()` — иначе он затенил бы `Personal.Print()`, и
  `main.go` печатал бы не то, что ожидается;
- `Parse` объявлен на указателе (`*Training`, `*DaySteps`), потому что изменяет структуру; `ActionInfo` — на значении,
  потому что только читает. Набор методов `*T` включает методы `T`, поэтому `&daySteps` и `&trains` удовлетворяют
  интерфейсу с обоими методами — это и используется в [`main.go`](cmd/tracker/main.go:38).

### 3.4 Встраивание указателя — осознанно

Из заметки: встраивание `*T` экономит копирование, но делает встроенные данные изменяемыми через значение-обёртку.

Применение: сознательно **не** встраиваем `*personaldata.Personal` — `Personal` мал, копирование дешево, а
неизменяемость персональных данных через копию структуры предпочтительнее.

## 4. Интерфейсы и утиная типизация

### 4.1 Неявная реализация интерфейса

«Если тип имеет вложенный тип, то он реализует все интерфейсы этого типа» и в целом реализация интерфейса в Go
неявная — достаточно иметь методы с нужными сигнатурами.

Применение: `DataParser` требует `Parse(string) error` и `ActionInfo() (string, error)`. `Training` и `DaySteps`
удовлетворяют ему без `implements`-объявлений, что позволяет [`Info`](internal/actioninfo/actioninfo.go:7)
работать с обоими типами одной функцией.

### 4.2 Интерфейс объявляет потребитель

Интерфейс принадлежит пакету-потребителю, а не пакету-реализации; это уменьшает связанность.

Применение: `DataParser` объявлен в [`actioninfo`](internal/actioninfo/actioninfo.go:1), а не в `trainings`/`daysteps`.

### 4.3 Узкий интерфейс

Интерфейс содержит ровно два метода — минимум, необходимый `Info`. Расширять его не следует: каждый лишний метод
сужает множество типов, которые можно передать.

### 4.4 Полиморфизм вместо `switch` по типу

Вместо проверки конкретного типа через рефлексию или type switch, `Info` вызывает методы интерфейса. Это и есть
идиоматичная замена наследованию.

## 5. Ошибки и валидация

Подходы, подтверждённые тестами проекта:

- **Валидация на границе**: `Parse` проверяет формат строки и положительность значений; расчётные функции
  [`spentenergy`](internal/spentenergy/spentenergy.go:1) повторно валидируют аргументы, потому что вызываются
  и напрямую (тесты, другие пакеты).
- **Нулевое значение при ошибке**: функции с `(float64, error)` возвращают `0` и ошибку; методы с `(string, error)` —
  пустую строку и ошибку. Тесты проверяют обе части результата.
- **Ошибка как значение, а не паника**: `errors.New`/обёрнутые ошибки из `strconv` и `time` возвращаются наверх.
- **Пробрасывание без потери контекста**: ошибка из `WalkingSpentCalories`/`RunningSpentCalories` возвращается
  из `ActionInfo` как есть.
- **Логирование на уровне оркестрации**: [`Info`](internal/actioninfo/actioninfo.go:7) не возвращает ошибку —
  логирует её и переходит к следующей итерации; это единственное место, где ошибка «поглощается» осознанно.

## 6. Стандартная библиотека вместо самописного

| Задача | Инструмент stdlib | Где |
|---|---|---|
| Разбор CSV-подобной строки | `strings.Split` | `Parse` в `trainings`/`daysteps` |
| Разбор целого числа с валидацией | `strconv.Atoi` | `Parse` |
| Разбор длительности (`1h30m`, `30.5m`) | `time.ParseDuration` | `Parse` |
| Перевод длительности в часы/минуты | `time.Duration.Hours/Minutes` | `spentenergy` |
| Форматирование чисел с 2 знаками | `fmt.Sprintf`/`Printf` с `%.2f` | `Print`, `ActionInfo` |
| Логирование ошибок | `log` | `Info` |

Принцип: не реализуем вручную то, что уже есть в stdlib; это снижает число дефектов и объём кода.

## 7. Рефлексия: когда не применять

Из [`Рефлексия — Яндекс Практикум.md`](../Рефлексия%20—%20Яндекс%20Практикум.md):

- рефлексия нужна, когда тип неизвестен на этапе компиляции (например, `encoding/json`);
- `reflect.DeepEqual` рекурсивно обходит значения и медленный — сравнение пишут вручную;
- `Value`-методы могут паниковать при неверном `Kind`; изменение возможно только для экспортируемых полей.

Применение в проекте: **рефлексия не используется**. Все типы известны статически, полиморфизм достигается
интерфейсом, сравнение значений — обычными операторами и `testify` в тестах. Теги структур не нужны: сериализации нет.

Осознанное исключение-ориентир: если бы потребовалось печатать произвольную структуру, сначала рассматриваем
интерфейс с методом `ActionInfo()`/`String()`, и только затем `reflect`.

## 8. Качество кода и процесс

### 8.1 Форматирование

`gofmt` — единственный стандарт форматирования; `goimports` дополнительно сортирует импорты.
Шаг финализации: `gofmt -l .` должен вернуть пустой список.

### 8.2 Линтинг

`go vet` — базовый линтер; ошибки `fmt.Printf` с несоответствующими глаголами и подозрительные конструкции
отлавливаются на шаге `go vet ./...`.

### 8.3 Документация

Экспортируемые сущности сопровождаются комментарием, начинающимся с имени сущности (`// Distance возвращает ...`),
чтобы `godoc` строил документацию. Комментарии — на русском, в стиле существующих комментариев в
[`spentenergy`](internal/spentenergy/spentenergy.go:7).

### 8.4 Тесты как контракт

Тесты — часть спецификации: имена полей, сигнатуры, формат вывода и граничные случаи берём из `*_test.go`.
Изменять тесты запрещено ([`agents.md`](agents.md:13), [`README.md`](README.md:5)).

### 8.5 Проверка на гонки данных

`go test -race ./...` — обязательная дополнительная проверка. Актуально потому, что
[`TestPrint`](internal/personaldata/personaldata_test.go:12) вызывает `Print()` в отдельной горутине, а
[`TestInfo`](internal/actioninfo/actioninfo_test.go:28) подменяет глобальные `os.Stdout` и `log` — код не должен
вводить собственных глобальных изменяемых состояний.

## 9. Чек-лист соответствия паттернам

- [ ] каждый пакет — одна директория, имя пакета = имя директории;
- [ ] экспортировано только то, что требует ТЗ; константы неэкспортируемые;
- [ ] нет новых внешних зависимостей; расчёты — на stdlib;
- [ ] `Personal` встроен без имени поля; собственный `Print()` не объявлен;
- [ ] `Parse` — на указателе, `ActionInfo` — на значении;
- [ ] интерфейс `DataParser` объявлен в пакете-потребителе и не расширен;
- [ ] ошибки возвращаются вместе с нулевым значением; логирование только в `Info`;
- [ ] рефлексия не используется;
- [ ] экспортируемые сущности задокументированы;
- [ ] `gofmt -l .` пусто, `go vet ./...` чисто, `go test -race ./...` зелёный;
- [ ] `cmd/tracker/main.go` и `*_test.go` не изменены.
